# Project integration and continuation

Use this guide when a lab uses running project code. The filename remains stable for earlier installations. Read the main skill for component cases, names, precision, and handover rules.

## Record the next operation

Read the lab README, request, and returned selection. Read the reviewer note first. Record question, baseline, chosen state, requested scope, constraints, open questions, source path, preview path, and next action.

Use the current mode: Explore, Adjust, Check edge cases, or Match a reference. Change mode in the same lab when the question changes. Mark superseded decisions explicitly. Do not treat a deliberate change of direction as a failed rule.

Identify reusable components, tokens, assets, fixtures, routes, panel code, and feedback UI by path or export. Record missing capabilities and intended changes. Read additional files only to resolve a specific unknown.

**Complete when:** the next operation has a source, boundary, and review criterion.

## Integrate the preview

Read the project's start instructions and package scripts. Reuse its package manager, route conventions, and available server. Inspect the target and direct dependencies. Do not replace working routing or install another router to host a lab.

Keep tool integration separate from production entry points when possible. Record created paths and integration patches. Preserve unrelated edits and shared consumers. Reuse source components and fixture data rather than a styled replica.

If the source cannot run, report the limitation. Offer an image-based lab when it can answer the question. Do not present that reconstruction as a verified running source.

Use managed background execution for a needed server. Check readiness within a bounded interval. Report the actual address. Do not assume port 3000 or terminate unrelated processes.

For standalone pages, copy runtime files beside the page. Preserve asset load order. Use system fonts or approved local assets. A served page cannot load `file://` font URLs. Verify font loading under the promised opening method.

**Complete when:** the intended preview runs at a known location or the exact setup failure is reported.

## Connect controls and cases

Bind each control to a verified target and domain. Use `contextual-inspectors.md` for selected parts and system rules. Label family or instance scope. Keep fixture selection independent from design selection.

Use the same component implementation across all applicable cases. Keep a fixture manifest and coverage record. A new variation does not require another component copy or another lab page.

For every new dimension, set its baseline deliberately. Earlier files use that value when the dimension did not exist. Preserve existing control keys and preset identities. Add and test migration before removing compatibility.

Use theme or purpose names for new variations. Put property differences in short descriptions. Preserve an earlier delta-based name only as a legacy saved-file identity.

**Complete when:** the reviewer can change the intended design across the declared cases and reproduce the selected fixture and scope.

## Verify the operation

Run relevant existing build, import, type, and state checks. Inspect rendered behavior separately. Operate changed controls and affected cases. Check unrelated targets and shared consumers when the patch can affect them.

For strict domains, validate every supported input path before applying values. The generic runtime is not a full design-system validator. Record adapters and any unresolved path.

For precision, control reference, viewport, scale, device-pixel ratio, fonts, assets, fixture, interaction state, and animation position. Capture comparable renders and measure differences. Record tolerance and residual mismatch. Do not infer exact measurements from a screenshot or a passing unit test.

Check floating tools without changing canvas width, wrapping, breakpoint, or scroll. Check visible bounds and menu clipping. Verify Light/Dark tools independently from product theme.

Save a mixed selection, inspect its JSON, and restore it in a fresh instance. Verify note, values, and required fixture/scope identifiers. Include the fixture manifest with the lab.

**Complete when:** each applicable check has evidence or an explicit Not tested result.

## Continue from feedback

Read selected state, reason, and next request as separate inputs. Preserve baseline and preferred pick. Keep options the reviewer still needs. Change only the affected design and checks.

Record the returned file, date, decision, and remaining question in the README. Copy that history into About. Increase round and reset revision when feedback starts the next cycle. Increase revision for later control, option, or preset changes.

A combined direction is a named configuration. It does not require a lettered synthesis branch or restarted interview. If the adjustment misses the intent, restore the saved pick and revise the disputed dimension.

**Complete when:** another reviewer can understand the next round without the original chat.

## Close or apply the decision

Record Chosen, Parked, or Rejected with a reason and the selected file or preset. Preserve the lab when work stops. Delete only explicitly authorized paths. Never revert unrelated work.

A review choice alone does not authorize production edits. For an authorized code application, transfer scoped values, show the destination diff, and validate it. For an image baseline, return changed values with units and the saved filename. Keep unconfirmed values labeled.

Update the current project record and lab index. State what changed, what was verified, what remains untested, and whether anything was applied outside the lab. Link the exact files and verified preview. Explain server requirements and folder-plus-selection sharing.

**Complete when:** the review record identifies both the selected design and its actual application status.
